# Карта модулей frontend

```bash
cd frontend
npm run modules:scan
npm run modules:check
```

Генератор сохраняет `docs/frontend-modules.json`. Формат версии 1 описан в
`docs/frontend-modules.schema.json`. JSON хранится в git; CI проверяет его актуальность.
После изменения вкладов или используемых зависимостей нужно повторить `modules:scan`.
В отчёте нет времени генерации и абсолютных путей, поэтому повторный запуск даёт тот же файл.

Можно задать другой конфиг frontend или выходной файл:

```bash
npm run modules:scan -- --project ./tsconfig.json --output /tmp/frontend-modules.json
```

`--check` сравнивает результат анализа с файлом и возвращает код 1, если файл отсутствует,
устарел или анализ встретил ошибку. Обычный запуск сохраняет отчёт даже с диагностикой,
возвращая код 1 при ошибках. `--help` выводит параметры.

## Что сканируется

Модуль — workspace из `frontend/package.json`: feature, shared package или host.
Для каждого модуля отчёт содержит:

- `name`, `kind`, `root`, `entrypoint`, `files`: идентификатор, расположение и реально
  проанализированные production-исходники. Next entrypoints из `src/app` относятся к host.
- `slots`: вложенное дерево экспортированного объекта `slots`. Листья — массивы компонентов
  с именем и расположением определения (`file`, `line`, `column`). Порядок массивов сохранён.
  Если модуль не экспортирует слоты, дерево пустое.
- `actions`: используемые callable-символы из `@camera-path/actions`, включая hooks,
  методы `useEditorActions()`, передачу обработчиков и локальные алиасы.
- `selectors`: вызовы hooks стора и API. `kind` различает `store-selector`, `store-hook`,
  `store-snapshot` и `api-hook`. `statePaths` для Zustand описывает выбранные поля:
  например, `camera.cameraMode`, `playback`, `tool.activeTool`.

У зависимости есть `package`, расположение `definition` и массив `usages` с файлом,
строкой, колонкой и исходным выражением. Для `getState()` определением служит общий
тип `EditorState`; места конкретных чтений находятся в `usages`. Строки и колонки начинаются с 1,
пути отсчитываются от `frontend`. Экспортное имя алиаса сохраняется для named imports;
namespace-доступ разрешается до исходного имени объявления. Поэтому разные экспортные
имена одного символа могут быть отдельными зависимостями с одним `definition`.

## Как устроен анализ

Используется TypeScript Compiler API: `createProgram`, AST и type checker с настройками
`tsconfig.json`. Алиасы путей, imports/re-exports и локальные ссылки разрешаются через
символы TypeScript. Поиск зависимостей не основан на регулярных выражениях. Код фич
не импортируется и не выполняется.

Объект слотов читается статически: поддержаны `as const`, `satisfies`, скобки,
ссылки на константы, namespace-компоненты, статические object/array spreads и вычисленные
строковые ключи. Циклы и построение слотов вызовами функций диагностируются, а не исполняются.

Именованные и inline Zustand-селекторы разбираются по AST, включая статические bracket keys,
деструктуризацию параметра и локальные алиасы. Для общих store hooks анализируются их
вызовы других hooks стора. Чтения `store.getState()` также учитываются, включая алиас snapshot.
`$` означает весь state, `*` — динамический ключ (с предупреждением). Пустой `statePaths`
у context hooks вроде `useProjectId` означает отсутствие определённого Zustand-пути;
неразрешимый callback селектора получает отдельную диагностику.

Тесты, type-tests, declaration files, `node_modules`, `.next`, сгенерированные API-клиенты
и DTO исключены из сканируемых модулей. Type checker может загружать их для разрешения типов.
Неиспользуемые и type-only imports, комментарии и строки не считаются обращениями к actions.

Это статическая карта прямых обращений production-кода, включая пока недостижимые функции;
она не показывает число runtime-вызовов и не строит React render tree. Внутренние зависимости
shared actions/API hooks не переносятся транзитивно в вызывающую фичу. Динамическая генерация
слотов, произвольные interprocedural dataflow и поля, вычисляемые сторонними callbacks,
не угадываются. Неподдержанные слоты и неразрешённые локальные/workspace imports попадают в
`diagnostics` как ошибки, неразрешённые селекторы — как предупреждения.
