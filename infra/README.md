# Camera Path AWS deployment (M3-2)

CDK v2 / TypeScript creates the complete backend infrastructure. No existing bucket,
VPC or application IAM identity is required. The standard CDK bootstrap stack and
the deployer's AWS credentials are prerequisites, not application resources.

## Architecture

- One AZ, one public subnet and Internet Gateway; **no NAT Gateway, CloudFront or ALB**.
- One `t3.small` Ubuntu 24.04 EC2 with Elastic IP, IMDSv2 and no SSH ingress.
- `api.<CP_DOMAIN>` A record in the existing public hosted zone selected by
  `CP_HOSTED_ZONE_ID`. Domain registration and that registrar-created zone remain
  outside this application stack; it never purchases a domain or creates a second zone.
- Nginx terminates HTTPS with a Let's Encrypt certificate. Port 80 serves HTTP-01
  challenges and redirects other requests to HTTPS; it never proxies plaintext API
  traffic. Uvicorn binds only to `127.0.0.1:8000`. SSE buffering is disabled; Nginx
  closes streams idle for 300 seconds.
- Encrypted 20 GiB root disk and separate encrypted 10 GiB EBS for SQLite.
- Private library bucket with `library/` IAM scope, direct browser S3 transfers and
  configurable CORS. An S3 gateway endpoint routes S3 traffic directly.
- Separate private backup bucket, Secrets Manager JWT/OpenAI secrets, and SSM access.
- S3 buckets, data volume and secrets use `RETAIN`; root disk is disposable.

EC2, public IPv4, EBS, Secrets Manager, S3 and deployment-provider resources have
their own AWS charges. An infrastructure update which replaces EC2/EBS is **not** a
normal code release: inspect `cdk diff` before applying it. A retained volume is not
automatically rediscovered after deleting and recreating the stack; restoration or
resource import is required. Keep the deployment ID stable for an environment.

## Prepare and deploy

Run from `infra/` with Node.js 24 and AWS CLI credentials authorized to deploy CDK.
The administrative AWS identity is used only on the developer's machine. Use your
configured profile or AWS CLI login session; an IAM username is not automatically
an AWS CLI profile. Confirm the identity with `aws sts get-caller-identity` first.
Do not commit environment values or contact information to the repository.

```bash
npm ci
export CP_DEPLOYMENT_ID=<your-deployment-id>
export CP_DOMAIN=<your-registered-domain>
export CP_HOSTED_ZONE_ID=<existing-public-zone-id>
export CP_TLS_EMAIL=<your-certificate-contact-email>
export CP_AWS_REGION=us-east-1
export CP_BACKEND_REVISION=$(git rev-parse HEAD)
export CP_FRONTEND_ORIGINS=http://localhost:3000,http://127.0.0.1:3000
npm run cdk -- bootstrap aws://<your-account-id>/us-east-1
npm run cdk -- diff
npm run cdk -- deploy
```

The revision must be a full, **already pushed** GitHub commit SHA. It defaults to
the local checkout's HEAD. For the first deployment use an already pushed branch or merged main commit that
contains the backend to run. The server fetches that exact SHA from
`https://github.com/vinneyto/camera_path.git`; it does not blindly pull a moving branch.
Application source is not shipped as a CDK asset. CDK does package the small Lambda
infrastructure provider into its bootstrap asset bucket.

Outputs include `ApiUrl`, `InstanceId`, `LibraryBucket`, `BackupBucket`,
`DataVolumeId`, `OpenAiSecretArn` and `BackendRevision`.

### Configure chat and the editor

The JWT secret is generated by Secrets Manager. The OpenAI secret is initially
empty, so geometry/read/auth endpoints deploy without an OpenAI key. Set its value
through Secrets Manager (console or `put-secret-value --secret-string file://...`;
do not commit or paste the key into a deploy command), then force a release check:

```bash
export CP_RELEASE_TOKEN=$(date -u +%Y%m%dT%H%M%SZ)
npm run cdk -- deploy
```

The script reads secret values on EC2, writes `/etc/camera-path/backend.env` with
mode 0600, and refreshes the service if the environment changed. Secret values are
not in the CloudFormation template, outputs or SSM command arguments. The plaintext
environment file is accessible to the application user and root.

Create/reset the single editor interactively through Session Manager, after the
first deployment (do not pass the password via CDK/SSM command arguments):

```bash
aws ssm start-session --region us-east-1 --target <InstanceId>
```

Inside the session:

```bash
sudo -u camera-path -H sh -c 'set -a; . /etc/camera-path/backend.env; set +a; cd /opt/camera-path/current/backend && exec .venv/bin/editor-create your-login'
```

For the Next.js proxy set `CAMERA_PATH_BACKEND_URL` to the output `ApiUrl`.
Add the production frontend origin to `CP_FRONTEND_ORIGINS` when deploying it.

## Stable AMI and backend releases (M4)

Use **`npm run cdk -- diff` / `npm run cdk -- deploy`** from `infra/`.
The npm entrypoint resolves the AMI and passes the concrete value as
`--parameters <stack-name>:BackendImageId=<resolved-id>` to the installed CDK CLI.
No manual AMI ID, AMI environment variable, context cache or state-saving step is
required. `BackendImageId` is an ordinary CloudFormation parameter of type
`AWS::EC2::Image::Id`, with **no default**. EC2 uses `Ref: BackendImageId`.
CloudFormation stores the supplied ID with the deployed stack.

The CLI is pinned to **2.1146.1**, which supports parameters for both diff and
deploy. Run `npm ci` after updating the checkout. Version 2.1129.0 did not forward
parameters into the diff change set. The wrapper forces `--method=change-set` for
diff, so a failed change-set comparison cannot fall back to a speculative template
diff. Direct `npx cdk diff/deploy`, alternate assemblies, manual BackendImageId
values, template-only comparisons and hotswap/watch are not this release workflow.

- **Existing stack / first adoption:** AWS CLI `DescribeStacks` reads the deployed
  `InstanceId` output; `DescribeInstances` reads that instance's actual `ImageId`.
  The same concrete ID is supplied to CreateChangeSet for diff and deploy. It is
  known when CloudFormation evaluates replacements, unlike GetAtt of a new SSM
  resource. No new SSM resource or ambiguous computed AMI reference is introduced.
- **New stack:** only the exact named-stack-not-found CloudFormation service error
  permits reading Ubuntu 24.04 amd64's public SSM `current` parameter. The chosen
  value is supplied automatically on creation. Once the stack exists, subsequent
  invocations use the deployed instance and never read Ubuntu `current`.
- AWS access/transport/JSON failures, missing/ambiguous instances or outputs,
  wrong accounts and unstable stack states abort before invoking CDK. They do not
  authorize a latest fallback. Deleting a stack creates a new environment; this
  mechanism does not restore/import its retained database volume.

`--profile NAME` / `--profile=NAME` is applied to both AWS CLI reads and CDK;
otherwise both use the active AWS profile/login. `CP_AWS_REGION` selects the target
region (default `us-east-1`). The wrapper supplies CDK's account from the verified
AWS identity. Log into the target account first; cross-account role overrides
are not supported. AMI selection performs only AWS reads. Standard CDK diff may
upload template assets and create/delete its unexecuted review change set.

The deployer needs `sts:GetCallerIdentity`, `cloudformation:DescribeStacks` scoped
to this stack, `ec2:DescribeInstances` (resource `*`, optionally region-restricted),
and `ssm:GetParameter` scoped to the regional public Ubuntu parameter for initial
creation. There are **no new SSM lifecycle grants**, application IAM changes or
release-provider IAM changes. Existing CDK bootstrap/asset/deployment permissions
remain necessary.

A plain image-ID parameter is deliberate: for SSM-typed CloudFormation parameters,
[UsePreviousValue preserves the key and reads its latest value](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cloudformation-supplied-parameter-types.html).
[DescribeInstances exposes the live ImageId](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-data-inventory.html).
Do not update the AMI parameter manually to upgrade the OS. AMI/OS upgrades and EC2
replacement need a separate reviewed operation. Ordinary releases do not patch
the OS, reboot EC2 or detach/migrate EBS.

### Review and release

**An exported `CP_BACKEND_REVISION` overrides HEAD**, even if it is an older SHA.
Unset it to follow the published checkout, or intentionally set a published full
SHA. Check the printed AMI, account, stack and revision before reviewing the diff.

```bash
# From infra/, with the existing environment/domain settings and target AWS login:
npm ci
npm run build
# Activate a Python environment containing boto3 before npm test.
PYTHONDONTWRITEBYTECODE=1 npm test
unset CP_BACKEND_REVISION  # or deliberately select an exact published SHA
npm run cdk -- diff
# Inspect the evaluated change-set diff before proceeding:
npm run cdk -- deploy
curl --fail --show-error https://api.$CP_DOMAIN/health
```

First adoption removes the old floating SSM template parameter and adds the plain
`BackendImageId` parameter, automatically set to the existing instance's AMI.
The required acceptance result is **no Backend replacement (including “may be
replaced”) and no InstanceId change for DatabaseAttachment or EIPAssociation**.
Stop if any appears. Do not deploy to discover whether the disk can be moved.
No manual AMI handoff or EBS migration is part of the transition.

After adoption, changing only the SHA changes BackendRelease / BackendRevision;
instance/UserData, EBS/attachment, EIP, network, secrets and application IAM stay
the same. Repeating the same SHA/config/AMI yields identical template/parameters.
`CP_RELEASE_TOKEN` intentionally triggers a rerun, e.g. after rotating a secret.
Exact-SHA preparation, stopped-writer backup, migrations, internal/HTTPS health
checks and recovery remain unchanged. The release does not require a reboot.

Local tests verify parameter selection/forwarding, actual pinned CLI support,
legacy resource identity, deterministic synthesis and absence of W9010 without
suppression. They do not prove AWS replacement evaluation. The operator performs
the real change-set-backed diff, checks the above acceptance result, deploys only
after review, and checks InstanceId/data/library continuity and external health.

EC2 user data bootstraps packages, Nginx, Certbot, the application user and systemd.
After Elastic IP association and the DNS record exist, the release command waits
for DNS to resolve to this IP, obtains the certificate using HTTP-01, validates
and reloads the Nginx HTTPS configuration, and enables `certbot.timer`. The renewal
deploy hook validates/reloads Nginx to load renewed certificates. DNS/certificate
failure aborts before backend migrations; initial HTTP setup exposes no API.
The EC2 role has **no Route 53 permissions**; CDK's deployer creates the A record. A small
asynchronous custom-resource provider waits for SSM, submits Run Command and waits
for its terminal status. It does **not** report deployment success when a command
has merely been submitted. Deleting this custom resource does not delete app data.

The root-owned release script:

1. Takes an exclusive release lock; verifies and mounts the expected EBS volume.
   Only an unformatted expected volume is initialized. UUID is saved in fstab.
2. Fetches the exact commit from GitHub into a bare repository, extracts it into a
   fresh release directory and runs `uv sync --frozen --no-dev --extra aws` there.
   All network/dependency preparation happens while the old app is still running.
3. Fetches secrets, stops the sole backend writer, creates a SQLite backup using
   the backup API (including committed WAL contents), checks its integrity, and
   uploads it into the backup bucket. Backup failure aborts before migration.
4. Runs Alembic with the new release's environment and dependencies.
5. Atomically switches `current`, starts systemd and verifies both internal `/health`
   and HTTPS `/health`, including certificate hostname/trust through local Nginx.
6. On migration/startup/health failure: stops the new writer, removes stale WAL/SHM,
   restores the snapshot and old environment, switches back to the previous code
   **and its venv**, starts and verifies it, then exits nonzero. The SSM failure makes
   `cdk deploy` fail. A failed restore leaves the service stopped and reports recovery
   failure, rather than running old code against an uncertain database.

On a failed first deployment there is no previous service to restart; a newly
created database is removed. Release logs are available in SSM Run Command and
service logs via `journalctl -u camera-path-backend`.

Recovery covers errors observed by the script, including subprocess timeouts. It
does not promise recovery after host failure, SIGKILL, storage failure or a forced
SSM termination; backups remain on EBS and S3 for manual recovery. `/health` is a
startup smoke check, not a full application acceptance test. S3 mutations are not
rolled back with SQLite: release scripts perform schema migrations, not app traffic.
There is brief downtime from stopping the writer through migration and healthcheck.

CloudFormation rollback is **not** a general database downgrade tool. Failure of
this release restores its own pre-release snapshot before signalling failure;
the subsequent callback for the previous SHA sees the restored healthy release.
An intentionally requested old commit or rollback after a successful release needs
a schema-compatible version or an explicit database restore plan. Never assume
`alembic upgrade head` reverses a newer migration. Keep external writers disabled
while backing up/restoring; the initial deployment uses one Uvicorn process.

## Instance AWS permissions

The instance has a custom inline policy rather than `AmazonSSMManagedInstanceCore`:

- Library: get/put/delete objects only under `library/`, list only that prefix.
- Backups: upload/abort multipart only under `database/`; no read, list or delete.
- Secrets: read/describe only this stack's JWT and OpenAI secret ARNs.
- SSM: `UpdateInstanceInformation` and four `ssmmessages` channel operations for
  modern SSM Agent Run Command and Session Manager. These use resource `*` as in
  AWS's minimal channel policy; no Parameter Store reads, inventory/patch actions,
  `SendCommand`, IAM, EC2 administration or DNS administration are granted.

The release-provider Lambda has its **own** role; its `SendCommand` grant targets
only this instance and the AWS RunShellScript document. It is not the EC2 role.
Account-level Session Manager settings requiring KMS/session logging need additional
scoped permissions; those integrations are not enabled by this stack.

## Local backend access to the CDK-created bucket

Set `CP_LOCAL_ACCESS=true` before deploying to include a restricted local IAM user
in the stack. The stack creates its permissions, **not a long-lived access key**.
Prefer temporary role/SSO credentials; if using this optional user, create and store
its key separately with AWS CLI. Do not write a secret key into stack outputs or Git.
Remove that key before disabling/deleting the optional IAM user.

The existing local backend needs only:

```dotenv
CAMERA_PATH_AWS_LIBRARY_STORAGE=s3
CAMERA_PATH_AWS_S3_BUCKET=<LibraryBucket output>
CAMERA_PATH_AWS_S3_PREFIX=library/
CAMERA_PATH_AWS_REGION=us-east-1
```

Supply credentials using the existing Boto3 configuration. EC2 automatically uses
its IAM role; developer credentials are never copied to the server. Because the
old bucket was deleted, old local library rows refer to missing files; use a fresh
local development database for a clean trial, or remove/recreate those assets.

## Verification

```bash
npm run build
python3 -m pip install 'boto3>=1.40,<2'
npm test
bash -n scripts/bootstrap.sh
```

Tests synthesize the stack without creating AWS resources and exercise actual
SQLite restoration after migration and health failures, failed backup upload,
failed recovery, WAL backup and successful activation. They also verify DNS timeout,
Nginx configuration restoration, renewal hook installation and restricted IAM. The GitHub Actions check
does not deploy. First real AWS deployment and browser/SSE acceptance are manual.

After a successful deploy, check externally:

```bash
curl --fail --silent --show-error https://api.<your-domain>/health
```

Inside Session Manager, verify renewal and services:

```bash
sudo certbot renew --dry-run
sudo systemctl status certbot.timer nginx camera-path-backend --no-pager
```

Renewal verification is a real-network check, not part of the local unit tests.
Port 80 must remain reachable for HTTP-01 renewal. Keep the registrar's name servers
pointing to this hosted zone. Changing the domain changes the endpoint; old DNS
records/certificates are not a frontend migration strategy.

## Email authentication infrastructure and deployment

Review and exercise the local SMTP flow from `backend/README.md` before deploying.
`npm run build` and the Node synth tests validate the SES/DNS/IAM declaration without
AWS access. The stack creates a SES domain identity for `CP_DOMAIN`, three Easy DKIM
CNAME records in `CP_HOSTED_ZONE_ID`, and MX/SPF records on `auth-mail.<CP_DOMAIN>`.
The existing API/frontend records remain in place. An existing domain DMARC record
is deliberately left untouched; manage any desired DMARC policy separately. Check
for pre-existing DKIM/MAIL FROM resources before deployment/import to avoid DNS or
SES identity conflicts.

EC2 gets only `ses:SendEmail` on SES identities in this AWS account and region,
restricted by `ses:FromAddress` to `noreply@<CP_DOMAIN>`. This includes verified
recipient identities which SES may also authorize in sandbox; a sender-domain-only
resource scope can fail with `AccessDeniedException` on the recipient identity.
There are no identity-management or `SendRawEmail` permissions. The application
always sends to the stored editor address. DNS management remains with CloudFormation. The release writes
production/email/SES settings and the region to `backend.env`; no AWS access keys
or passwords are added. `AuthEmailFrom` is a non-secret stack output.

After the PR is merged and locally accepted, use your existing deployment variables
(`CP_DEPLOYMENT_ID`, `CP_DOMAIN`, `CP_HOSTED_ZONE_ID`, `CP_TLS_EMAIL`, frontend origins,
AWS account/profile) and the exact desired published commit:

```bash
export CP_BACKEND_REVISION=$(git rev-parse HEAD)
cd infra
npm ci
npm run cdk -- diff
npm run cdk -- deploy
```

Wait for actual SES identity verification, not merely CloudFormation completion:

```bash
aws sesv2 get-email-identity --email-identity "$CP_DOMAIN" --region us-east-1
aws sesv2 get-account --region us-east-1
```

`VerifiedForSendingStatus` must be true; check DKIM status as well. If the account
is still in sandbox, verify the sole editor's recipient address (the CLI sends an
AWS confirmation message which the recipient must accept):

```bash
aws sesv2 create-email-identity --email-identity you@example.com --region us-east-1
```

For the initial single-editor deployment, sandbox is sufficient once both the
sender domain and recipient are verified. Production access is a separate,
one-time SES account/region request, reviewed by AWS; do not submit it on every
CDK deployment. Request it through the SES console when unverified recipients are
needed. See https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html.

After successful deploy, use SSM Session Manager to replace a legacy editor login
with an email. Keep the password interactive (never in command arguments/outputs):

```bash
sudo -u camera-path sh -c 'set -a; . /etc/camera-path/backend.env; set +a; cd /opt/camera-path/current/backend; .venv/bin/editor-create you@example.com'
```

Deploy the updated frontend too: it understands challenge responses and sets the
HttpOnly cookie only after code confirmation. Browser acceptance: login sends a
real email, password alone cannot edit, correct code enables editing, sign out
revokes the session, resend invalidates the previous code, and a delivery error
never grants access. Domain attachment for the frontend is a separate M3-7 task.
